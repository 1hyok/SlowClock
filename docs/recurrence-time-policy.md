# v1 반복 일정 시간대 호환 정책

기존 일정의 epoch와 완료 날짜를 보존한다. v1 문서에는 생성 당시 시간대나 별도의 벽시계 시각이 없으므로, 기존 값을 특정 지역의 오전 8시로 다시 해석하거나 이동 뒤 오전 8시로 이행하지 않는다. 이 문서는 현재 동작의 호환 기준이며 여행지의 같은 시각에 울리는 기능을 추가하는 결정이 아니다.

## 계산과 이미 예약된 알람

- `Schedule.startTime`은 첫 회차의 절대 시각이다. 단발 일정과 이미 AlarmManager에 예약한 시각은 시간대만 바뀌어도 같은 epoch를 유지한다.
- 반복 회차를 새로 계산할 때는 `Calendar.getInstance()`가 선택한 시간대·달력으로 첫 회차를 읽고, 그 시·분·초와 요일 또는 일자를 대상 날짜에 적용한다. 일반적인 기기 설정에서는 현재 기기 시간대다. Android 13 이상에서 locale에 `tz` 확장이 있으면 Calendar가 이를 사용할 수 있다.
- 예: 서울 2026-01-06 08:00은 LA에서 2026-01-05 15:00이다. LA에서 계산하는 매일 회차는 15:00, 매주 회차는 월요일이다. 생성 당시 화요일 08:00을 저장한 별도 필드는 없다.
- 시간대 변경만으로 재예약하지 않는다. 기존 예약과 이후 앱 복원·동기화·다음 회차 계산을 구분한다. `TIMEZONE_CHANGED` 수신을 추가하는 것만으로 모든 회차가 여행지의 생성 시각을 유지하지는 않는다.
- `completedDates` 키는 회차를 계산한 달력 날짜다. 기존 키를 이동시키지 않으므로 시간대를 옮긴 날에는 화면의 날짜·완료 회차가 달라질 수 있다.
- 반복 종료 시각은 시작에서 떨어진 **경과 시간**을 보존한다. DST 경계를 넘는 날에는 시작과 종료의 벽시계 간격이 다를 수 있다.

## DST 경계

같은 시간대에서 존재하는 시각은 달력 날짜를 따라 반복한다. 따라서 DST 시작일의 아침 회차는 전날보다 23시간 뒤일 수 있고 종료일은 25시간 뒤일 수 있다. 존재하지 않거나 두 번 있는 시각은 기존 Calendar의 기본 lenient 해석을 보존한다.

`RecurrenceTimeZoneTest`는 명시적인 offset으로 만든 기대 epoch를 사용해 서울→LA 이동, 단발 epoch, 회차 키, DST 시작, 공백·중복 시각을 검증한다. 공백·중복의 구체 offset은 호스트 JDK Calendar의 회귀 결과다. 모든 Android/OEM·시간대 데이터 버전의 동작을 실측했다는 뜻은 아니다. 실기기 검증은 별도 진행한다.

향후 여행지의 같은 벽시계 시각 또는 생성 지역의 시각을 제품 기능으로 선택한다면, 시간대·벽시계 필드, DST 공백/중복 정책, 완료 키와 기존 문서 이행을 함께 설계해야 한다. 현재 문서에서 누락된 생성 시간대를 추정해 기존 알람을 이동시키지 않는다.

근거: [Android Calendar.getInstance와 기본 leniency](https://developer.android.com/reference/java/util/Calendar), [AlarmManager RTC epoch](https://developer.android.com/reference/android/app/AlarmManager#RTC_WAKEUP).
